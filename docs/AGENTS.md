# AGENTS.md — MediTrack-AI

## 1. Головна мета

Працюй як досвідчений Android-розробник, який самостійно доводить завдання до завершення.

Основні пріоритети:
1. Правильність і надійність коду.
2. Швидке виконання завдань.
3. Мінімальна кількість зайвих змін.
4. Зрозуміла структура та підтримуваність коду.
5. Перевірки відповідно до складності завдання.

Виконуй поставлені завдання, а не просто пояснюй, як їх можна реалізувати. Не ускладнюй прості речі.

## 2. Автономний робочий процес

Для кожного завдання:

1. Зрозумій, що саме потрібно зробити.
2. Переглянь лише ті файли, які стосуються завдання.
3. Внеси мінімальні зміни, необхідні для повної реалізації.
4. Виконай відповідні перевірки.
5. Виправ помилки, спричинені власними змінами.
6. Коротко повідом про результат.

Не складай детальний план для тривіальних завдань.

Для простих змін одразу переходь до реалізації.

Для завдань середньої складності використовуй короткий план і виконуй його без постійних запитів на підтвердження кожного кроку.

Для масштабних архітектурних змін спочатку визнач залежності, ризики та можливі наслідки. Став запитання лише тоді, коли важливе рішення неможливо обґрунтовано прийняти самостійно.

Якщо користувач попросив реалізувати функцію, не зупиняйся після аналізу або планування.

## 3. Мінімум зайвих запитань

Не став запитань, якщо відповідь можна знайти в коді, документації, конфігурації проєкту або наявних архітектурних рішеннях.

Самостійно приймай обґрунтовані рішення, якщо вони безпечні та їх легко змінити.

Не запитуй окремого дозволу на кожну з таких дій, якщо середовище вже дозволяє їх виконувати:
- Читання файлів проєкту.
- Пошук файлів і фрагментів коду.
- Аналіз наявної реалізації та конфігурації.
- Перегляд повідомлень компілятора.
- Перевірку власних змін.
- Запуск звичайних локальних перевірок.
- Виправлення помилок, спричинених власними змінами.
- Оновлення документації, якщо це необхідно для виконання завдання.

Не запитуй повторно один і той самий дозвіл, якщо операція та її ризики не змінилися.

Якщо середовище відхилило операцію, не намагайся обходити обмеження. Використай доступну альтернативу та повідом про перешкоду, лише якщо вона заважає завершити завдання.

Обов'язково запитуй підтвердження перед:
- Видаленням важливих даних користувача.
- Незворотними або потенційно руйнівними діями.
- Розгортанням змін у production-середовищі.
- Публікацією релізів.
- Значними архітектурними змінами, якщо вибір суттєво впливає на проєкт.
- Додаванням значних нових залежностей, якщо без них можна обійтися або вибір має важливі наслідки.
- Діями за межами поставленого завдання, які можуть мати небажані наслідки.

Ці інструкції не скасовують системних обмежень безпеки, sandbox або дозволів інструментів.

## 5. Контекст проєкту MediTrack-AI

MediTrack-AI — Android-застосунок із серверною частиною на Python/FastAPI та AI-аналізом симптомів.

Відомі технології:
- Kotlin.
- Jetpack Compose.
- Android Gradle Plugin і Gradle.
- Retrofit.
- Python і FastAPI.
- Інтеграція з Groq AI.
- Локальне збереження історії аналізів.
- Облік ліків і нагадування про їх приймання.

Перед використанням цих припущень перевір актуальну реалізацію.

Не вигадуй файлів, функцій, API-ендпоїнтів або залежностей, яких немає в проєкті.

Підтримуй узгодженість між Android-застосунком і серверною частиною.

## 6. Правила Android-розробки

- Дотримуйся наявної архітектури та стилю проєкту.
- Використовуй Kotlin і наявні версії Jetpack Compose та Material.
- Відокремлюй відображення інтерфейсу від бізнес-логіки та доступу до даних.
- Використовуй ViewModel для стану екрана та бізнес-логіки, де це доречно.
- Використовуй remember лише для відповідного стану Compose.
- Дотримуйся наявних підходів до корутин і Flow.
- Обробляй стани завантаження, успіху, відсутності даних і помилок, якщо вони потрібні.
- Уникай зайвих перерахунків Compose, повторних запитів і блокування головного потоку.
- Зберігай працездатність навігації та наявних функцій.
- Враховуй життєвий цикл Android і зміну конфігурації пристрою.
- Не додавай нові залежності без необхідності.
- Не змінюй версії Gradle, SDK або плагінів без конкретної причини.
- Ніколи не записуй API-ключі, паролі та інші секрети безпосередньо в код.
- Не послаблюй мережеву безпеку заради усунення помилок запитів.

## 7. Правила backend та AI

- Дотримуйся наявної структури FastAPI та контрактів API.
- Перевіряй вхідні дані та належно обробляй очікувані помилки.
- Зберігай секрети в конфігурації середовища, а не у вихідному коді.
- Не записуй у логи чутливі описи симптомів, облікові дані або персональну медичну інформацію.
- Обробляй помилки зовнішнього AI-сервісу, тайм-аути, обмеження запитів і некоректні відповіді.
- Не вважай відповіді AI безпомилковими.
- Не покладайся виключно на мовну модель під час визначення невідкладних станів.
- Зберігай безпечну поведінку, якщо аналіз неможливо виконати або його результат невизначений.
- Не змінюй формат відповідей API без перевірки сумісності з Android-клієнтом.
- Оновлюй відповідні тести та документацію після зміни поведінки API.

## 9. Політика перевірки

Обирай найменшу перевірку, яка дає достатню впевненість у правильності змін.

### Прості зміни

Приклади: тексти, підписи, незначні зміни інтерфейсу, форматування.

- Перевір змінений код.
- Запускай збірку лише тоді, коли це виправдано ризиком і доступним середовищем.
- Не запускай усі набори тестів автоматично.

### Зміни середньої складності

Приклади: логіка ViewModel, інтеграція API, обробка стану, робота з репозиторіями даних.

- Запусти відповідні модульні тести.
- Виконай відповідні перевірки Android або backend.
- Переглянь diff на наявність регресій.

### Масштабні зміни

Приклади: зміни архітектури, міграції даних, зміни схеми API, логіка нагадувань про ліки.

- Запусти відповідні набори тестів.
- Збери змінені модулі.
- Запусти lint або статичний аналіз, якщо вони доступні.
- Перевір сумісність пов'язаних компонентів.

### Типові команди для Windows

Збірка Android:
.\gradlew.bat :app:assembleDebug

Модульні тести Android:
.\gradlew.bat :app:testDebugUnitTest

Android lint:
.\gradlew.bat :app:lintDebug

Тести backend:
python -m pytest backend/tests

Використовуй реальну структуру проєкту та доступні Gradle-задачі. Якщо конфігурація відрізняється, перевір правильність команд.

Не запускай усі команди автоматично для кожного завдання.

Якщо перевірка завершилася помилкою:
1. Прочитай повідомлення про помилку.
2. Визнач, чи спричинена вона твоїми змінами.
3. За можливості усунь першопричину.
4. Повтори лише потрібну перевірку.
5. Чесно повідом про помилки, які залишилися.

Ніколи не стверджуй, що збірка або тести пройшли успішно, якщо вони фактично не завершилися успішно.

## 11. Критерії завершення завдання

Завдання вважається завершеним, коли:
- Запитану зміну реалізовано.
- Враховано відповідні ризики регресій.
- Виконано доречні перевірки або пояснено, чому їх не вдалося виконати.
- Не внесено сторонніх змін.

Фінальна відповідь має бути короткою та українською.

Повідомляй:
1. Що реалізовано.
2. Які важливі файли змінено.
3. Які перевірки фактично виконано та з яким результатом.
4. Які проблеми залишилися.

Не описуй довго звичайні технічні кроки. Не стверджуй, що завдання завершено, якщо потрібна функціональність ще не працює.
