# ЛР5 — Архітектура FastAPI

Погоджено користувачем 17.10.2026. Варіант Б; сценарій — аналіз симптомів з уточненнями. Поточні незакомічені зміни зберігати. Android, формат наявних JSON-полів, категорії, промпт і призначення сценарію не змінювати. Коміт, push і deploy не входять у задачу.

## Початкові проблеми

1. `backend/main.py:analyze_symptom` напряму залежить від `categorize_symptom`, нормалізує опис і перетворює помилки.
2. `backend/ai_service.py` поєднує отримання конфігурації, HTTP до Groq і перетворення результату; немає інтерфейсу зовнішньої залежності.
3. `.env` завантажується в main.py та ai_service.py; модель/таймаут розкидані константами. Моделі API не відділені від типізованого прикладного результату; тест підміняє глобальну функцію замість DI.

## Файли

- Нові: `backend/domain.py` — незалежні dataclass, AIProvider Protocol, domain errors; `config.py` — єдині налаштування; `analysis_service.py` — сценарій; `dependencies.py` — FastAPI Depends; `fake_provider.py` — синтетичні успіх/помилка без мережі.
- Оновити `backend/ai_service.py` до GroqProvider; `models.py` залишити HTTP-схемами з явним mapping; `main.py` — маршрути та централізовані HTTP-handlers. Оновити `.env.example`, не читати/публікувати справжній ключ.
- Тести: адаптувати `backend/tests/test_ai_service.py`; додати `test_analysis_service.py`, `test_api.py`. `backend/requirements-dev.txt` — HTTPX для TestClient, без зміни runtime-залежностей.
- Після перевірки рефакторингу додати `backend/request_context.py`: request_id у X-Request-ID і логах, без медичних текстів/секретів та без зміни JSON.
- Оновити README, docs/architecture.md, decisions.md, ROADMAP.md, api-contract.md, ai-component.md, testing.md, known-limitations.md. Фактичні результати — у changelog.md цієї задачі.

## Послідовність і критерії

1. Запустити наявні 15 backend-тестів як baseline. Зафіксувати поля успіху, context_used, 400/422/503 та контрольовану 500. Зберегти наявну семантику до окремого рішення про валідацію trim.
2. Виділити domain/config/provider/service/DI; перевірити попередній сценарій без зовнішнього AI. Fake передавати через той самий інтерфейс, не використовувати як мовчазний fallback.
3. Після успішної перевірки додати контрольне розширення request_id та його HTTP-тест. ID генерується сервером, не копіює довільний клієнтський ввід.
4. Щонайменше п’ять змістовних тестів: успіх, доменна помилка, таймаут, некоректна відповідь, контекст/DI; окремо request_id у відповідях і логах. Усі AI-виклики в автоматичних тестах — fake/mock.
5. Одна фінальна перевірка backend, перегляд diff, оновлення KB. Демонстраційні матеріали з fake позначати синтетичними; реальний наскрізний Groq/телефон/deploy не позначати виконаним без фактичного запуску.
