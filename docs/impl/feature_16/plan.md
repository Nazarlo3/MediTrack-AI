# ЛР6 — структуровані дані симптому

Погоджено користувачем 20.10.2026: спочатку виправити пункт 1 (ЛР6). Попередній етап feature_15 залишити як історичні докази; оцінювання наявної 0.3 не вважати новою AI-функцією.

## До реалізації

- Baseline: поточна 0.3 з 16 категоріями/уточненнями, SYSTEM_PROMPT з `backend/evaluation/current.json`, max_tokens=400. HEAD `c1eff7f`. Зберегти новий окремий знімок до редагування AI.
- Нове розширення: необов'язкові `duration_days` (ціле 1–30) та `intensity` (ціле 0–10, суб'єктивна вираженість симптому). Без них старий сценарій залишається. Це додаткові дані для інформаційного пояснення, не діагностична шкала; жодних нових медичних порогів терміновості.
- Контракт: той самий POST, два необов'язкові поля; server-owned `details_used` у відповіді підтверджує їх передачу, але не правильність AI. Новий Android відхиляє непідтверджену підтримку замість тихого ігнорування старим сервером.
- До нових запитів зафіксувати `backend/evaluation/details/cases.json`: 5 спільних регресій із feature_15 + 5 нових синтетичних прикладів. Основний травматичний приклад однозначний; монітор лишається лише в старому наборі як неоднозначний крайовий випадок.
- Критерії ДО реалізації: 5/5 спільних категорій; 5/5 нових сценаріїв з очікуваною категорією, фактичними значеннями у поясненні й details_used=true; 10/10 структурно коректних відповідей. Окремо рахувати HTTP-збої/затримку; перший невдалий прогін не приховувати. Це інженерна відповідність, не клінічна точність. Значення параметрів не мають самі по собі автоматично задавати urgency.

## Файли та порядок

1. Backend: змінити `domain.py`, `models.py`, `analysis_service.py`, `ai_service.py`: strict validation, підготовка окремого повідомлення з атрибутами, правила використання/невідомих значень, підтвердження підтримки. Розділення service/provider та помилки зберегти.
2. Android: domain/network `SymptomModels.kt`, `SymptomMapper.kt`, `AnalyzeSymptomUseCase.kt`, `DefaultSymptomRepository.kt`, controller/ViewModel/UiState; додати два поля в `SymptomCheckScreen.kt`. Значення rememberSaveable; зберігати з описом історії й у контексті, не міняти JSON-схему історії. Retry/clarify зберігають початкові параметри, cancel — чернетку. Ліки не змінювати.
3. Перевірки: доповнити наявні backend/API та JVM-тести валідації, мапінгу, сумісності, retry/history. Оновити runner `--suite details`, знімки baseline/current і зберегти реальні порівняння в окремій папці. Старі результати не перезаписувати; залежності/версію APK не змінювати.
4. Один погоджений телефонний сценарій (якщо пристрій доступний): актуальний debug APK через install -r без очищення даних, ізольований UI → локальний FastAPI → Groq, поля/результат/уточнення/історія, максимум 2 фото. Оновити opt-in метод у `Lab5PhoneScenarioTest.kt`.
5. Оновити лише документацію ЛР6/контракт/README/testing/ROADMAP та короткий Word-звіт ЛР6 з новими порівняннями. Старі звіти ЛР1–5 поки не редагувати. План і журнал — feature_16; зафіксувати всі фактичні результати та межі.
6. Переглянути diff; не виконувати commit/push/deploy/публікацію APK без окремого запиту. Попередні локальні зміни зберегти.
