# План виправлення Feature 5: Надійне збереження, прийом ліків і валідація форм

## 🎯 Мета

Виправити три локальні проблеми Android-застосунку без повного рефакторингу та без зміни API backend:

1. зробити локальне збереження історії та ліків послідовним і безпечним;
2. прив’язати статус «Прийнято» до конкретної дати;
3. узгодити й посилити валідацію форм.

Зберегти сумісність із наявними даними в `SharedPreferences`, фотографіями ліків і поточним сценарієм аналізу симптомів.

---

## 📐 Покроковий план

### Крок 1: Аналіз і підготовка локального сховища

- Перевірити фактичний Git-стан перед змінами.
- Винести послідовне читання, запис і міграцію локальних даних у невеликий внутрішній компонент.
- Не додавати сторонні залежності.
- Не видаляти старі ключі, доки новий формат не буде успішно записаний.

### Крок 2: Надійне збереження історії та списку ліків

- Серіалізувати операції додавання, видалення, перемикання статусу та очищення.
- Не дозволяти старішій фоновій операції перезаписати новіший стан.
- Зберегти поточні ключі `symptom_history` і `medications_list_v1` або виконати контрольовану міграцію.
- Підтвердити, що швидкі послідовні зміни та перезапуск застосунку не гублять дані.

### Крок 3: Модель прийому ліків за датою

- Додати поле дати останньої позначки прийому або еквівалентну структуру, сумісну з Gson.
- Вважати препарат прийнятим лише для поточної дати.
- Не приписувати старому `isTaken = true` невідому дату під час міграції.
- Зберегти наявні ID, фото, назви, дозування, графік і кінцеві дати.

### Крок 4: Валідація форм і стану UI

- Опис симптому: після обрізання пробілів від 3 до 500 символів.
- Дата: строгий формат `ДД.ММ.РРРР`, реальна календарна дата, без минулої дати для нового курсу.
- Час: коректний формат `HH:mm`.
- Дні тижня: перевірка підтримуваних значень і запасний варіант `Щодня`.
- Не створювати препарат, якщо копіювання вибраного фото завершилося помилкою.
- Заблокувати повторне збереження форми під час асинхронної операції.
- Зберігати введені поля та вибрану вкладку під час конфігураційних змін екрана.
- Не перехоплювати `CancellationException` як звичайну помилку.

### Крок 5: Тести та документація

- Додати тести для валідації, міграції, дат і послідовних операцій збереження.
- Перевірити ручні сценарії для старих даних, нового дня, очищення історії та фото.
- Після реалізації заповнити `changelog.md` лише фактично виконаними змінами.
- За потреби оновити `docs/changelog.md`, `docs/architecture.md`, `docs/decisions.md`, `docs/testing.md` і `docs/known-limitations.md`.

## ✅ Definition of Done

- Історія та список ліків не втрачають зміни при швидких послідовних діях.
- Старі записи завантажуються без крашу та не втрачають доступні поля.
- Статус прийому коректно скидається для нового дня.
- Некоректні опис, дата, час і дні не зберігаються.
- Введені значення форми переживають поворот екрана.
- Проходять unit-тести, `lintDebug`, `assembleDebug` і `assembleRelease`.
- У changelog описані тільки перевірені зміни та відомі обмеження.

## ⚠️ Ризики

- Старий формат `isTaken` не містить дати, тому його не можна достовірно відновити як прийом за конкретний день.
- Наявні `content://` URI зі старих записів можуть залишатися недоступними після перезапуску; нові фото мають продовжити зберігатися у внутрішньому сховищі.
- Якщо компіляція або тести виявлять несумісність із поточними версіями Android Gradle Plugin, зміни будуть зупинені до окремого узгодження.
