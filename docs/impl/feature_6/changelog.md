## 12.10.2026 — Реалізація після підтвердження користувача

### Зміни

- Додано `reminders/MedicationSchedule.kt`: строгий розбір наявного часу, дні тижня/вихідні, кінцева дата включно, статус прийому за датою, локальні часові пояси та DST.
- Додано `MedicationReminderScheduler.kt`: одноразові alarm, окремий production-канал, стабільні ID, скасування, збережені службові метадані та захист від повторного повідомлення за локальну дату. Точний alarm за доступу, приблизний — без нього.
- Додано `MedicationReminderReceiver.kt` і `ReminderRestoreReceiver.kt`: актуальне читання запису, повідомлення з відкриттям застосунку, наступний прийом і системне відновлення. Асинхронна робота receiver обмежена 8 секундами з `goAsync`/`finish`.
- Додано `ic_medication_notification.xml` і 7 тестів `MedicationScheduleTest.kt`.
- У manifest додано `SCHEDULE_EXACT_ALARM`, `RECEIVE_BOOT_COMPLETED`, production receiver та системні події відновлення.
- `SymptomViewModel.kt` звіряє графік після читання й успішного додавання, видалення та зміни статусу ліків.
- `MedicationSection.kt` показує стан дозволів, кнопки дозволу сповіщень/точного часу та оновлення графіка. Після повернення з налаштувань графік оновлюється. Старий запис без часу і завершений курс мають пояснення в картці.
- Оновлено README, requirements, architecture, testing, known-limitations, decisions, project-overview та загальний changelog. `project-overview.md` додано до переліку плану після виявлення в ньому застарілого твердження; уточнення повідомлено користувачу до зміни.
- Модель/JSON препаратів, backend, API та Gradle-залежності не змінювалися в межах feature_6. Debug-меню збережено окремо.

### Перевірки

- Перший запуск Gradle не відбувся: у терміналі немає `JAVA_HOME`/`java` у PATH. Повторний запуск використовував JDK Android Studio через змінну середовища лише процесу, без редагування проєкту.
- Команда: `.\gradlew.bat :app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleRelease` — `BUILD SUCCESSFUL`.
- Нові тести графіка: 7, помилок/пропусків 0. Наявні тести також пройшли.
- Lint: 0 помилок, 41 попередження. Серед нових — рекомендації UseKtx та ApplySharedPref; синхронні службові записи виконуються на Dispatchers.IO для контролю їх завершення.
- Переглянуто підключення до ViewModel, manifest, метадані alarm і сценарій кінця курсу: останнє показане повідомлення не видаляється лише через відсутність наступного прийому.
- `git diff --check` — без зауважень. Коміт та push не виконувалися.

### Межі перевірки

- Реальна доставка production-повідомлень, reboot, відмови в дозволах і release на телефоні поки не перевірені. Debug-тест користувача був виконаний до feature_6 і не підтверджує цю функцію.
- Один час на препарат за день; без автоматичного надолуження пропущених прийомів. Старим записам без часу не призначається довільна година.
- Без точного дозволу можлива затримка. Force stop і обмеження виробника можуть блокувати доставку.
- Дата повідомлення резервується перед показом, тому немає гарантії «рівно один раз»: аварія між записом і notify може спричинити пропуск.
- Подальші ручні результати додавати тільки після фактичної перевірки.

## 13.10.2026 — Виправлення скидання очікуваного нагадування

- Користувач повідомив, що після попереднього виправлення кілька нових препаратів не дали production-сповіщень. Дозволи на сповіщення й точний час надані, кнопку «Оновити нагадування» натискали неодноразово. Повідомлення про наданий доступ підтверджує дозволи, але не факт доставки.
- Аналіз коду виявив можливу причину: ручне оновлення примусово скидало графік. Якщо Android затримував сьогоднішній alarm, наступне планування переносило той самий `PendingIntent` на завтра. Точну причину на телефоні без підключеного пристрою й журналу подій не підтверджено.
- Ручне оновлення більше не скидає очікуваний сьогоднішній alarm; та сама умова збереження застосовується до автоматичної звірки. Прапорець помилки доставки знімається лише після успішного виклику `notify()`, а не після натискання кнопки; текст стану більше не обіцяє, що кнопка усуне помилку доставки.
- Додано 2 регресійні unit-тести для затриманого, застарілого й уже доставленого alarm. `:app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleRelease` — `BUILD SUCCESSFUL in 1m 7s`; 16 тестів, 0 помилок/пропусків; lint: 0 помилок, 41 попередження.
- Після цього виправлення доставку на телефоні ще потрібно повторно перевірити. Дані ліків, модель, API й залежності не змінювалися; commit/push не виконано.
