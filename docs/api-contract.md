# API Contract — MediTrack AI

## 20.10.2026 — тривалість та інтенсивність (ЛР6)

Той самий `POST /analyze-symptom` додатково приймає необов'язкові `duration_days` (ціле 1–30) та `intensity` (ціле 0–10, суб'єктивна вираженість). Можна передати одне поле, обидва, null або не передавати. Строки, boolean, дроби й значення поза межами дають 422 до AI-виклику. Старі description/context працюють без цих полів; їхні попередні обмеження збережені.

```json
{"description":"Вдарив гомілку об край ліжка, болить у місці удару.","duration_days":3,"intensity":5}
```

В успішну відповідь додано server-owned `details_used`: true, якщо хоча б одне валідне поле передано провайдеру (включно з intensity=0), інакше false. Попередні шість полів залишаються. Це підтвердження передачі, не точності AI; значення у поясненні перевіряються окремо.

Новий Android вимагає details_used=true, коли надіслав параметри. Старий backend, який їх проігнорував, не створює помилково успішний запис: UI просить оновити сервер або прибрати поля. Для опису без параметрів старі відповіді приймаються. При уточненні передаються початкові параметри й попередній context; вільний текст може виправити початкові відомості, це обумовлено у промпті. Retry повторює ті самі дані.

Потрібне окреме розгортання backend; нові локальні файли самі по собі Render не оновлюють. Endpoints, медичні пороги, ліки й формат старої історії не змінено.

## 2. Analyze Symptom
Основний ендпоінт аналізу та категоризації симптому.

- **Method:** `POST`
- **Path:** `/analyze-symptom`
- **Headers:** `Content-Type: application/json`

### Request Body
```json
{
  "description": "болить голова і нудить"
}
```

### Success Response (`200 OK`)
```json
{
  "category": "загальне нездужання",
  "explanation": "Поєднання головного болю та нудоти є неспецифічними симптомами, які часто вказують на загальний стан нездужання.",
  "urgency": "звичайне",
  "disclaimer": "Це не медичний діагноз. У разі проблем зі здоров'ям зверніться до лікаря."
}
```

### Error Responses

#### `400 Bad Request` (Опис лише з пробілів)
Наприклад, `{"description":"   "}` проходить перевірку початкової довжини Pydantic, але стає порожнім після `strip()` в обробнику.

```json
{
  "detail": "Опис не може бути порожнім"
}
```

#### `422 Unprocessable Entity` (Помилка валідації Pydantic)
Опис коротший за 3 або довший за 500 символів (зокрема `""`) відхиляється Pydantic із масивом помилок у `detail`. Backend перевіряє початкову довжину до `strip()`, Android — довжину після обрізання крайніх пробілів. Пробільне доповнення короткого непорожнього тексту backend повторно за довжиною не перевіряє.

#### `503 Service Unavailable` (Збій AI-сервісу)
Нижче один із можливих текстів `detail`; для таймауту та некоректної AI-відповіді повідомлення відрізняються.

```json
{
  "detail": "AI-сервіс тимчасово недоступний"
}
```

#### `500 Internal Server Error`
Неочікувана помилка: `{"detail":"Внутрішня помилка сервера. Спробуйте пізніше."}`.

Успішний JSON є прикладом формату, а не протоколом тестування. Очікувані значення `urgency`: `звичайне`, `увага`, `терміново`; категорії описані в [ai-component.md](ai-component.md).

## 16.10.2026 — Розширення значень category

Форма POST-запиту й відповіді не змінена. До попередніх семи категорій додано дев’ять — повний перелік у [ai-component.md](ai-component.md). Android має приймати весь перелік до оновлення backend; поточний валідатор і сервер перевіряються на однаковість наборів. Невідома urgency або відсутні/неповні поля у Groq-відповіді спричиняють контрольовану 503 замість небезпечного автоматичного значення «звичайне». Невідома категорія, як раніше, переходить у «інше».

## 17.10.2026 — Уточнення з контекстом

POST /analyze-symptom зберігає обов'язковий description (3–500). Необов'язковий context за замовчуванням []: до 6 попередніх повідомлень, повні пари user/assistant, починаючи з user. Кожне content — непорожній текст до 1500 символів. Інші ролі, порушення порядку або лімітів відхиляються Pydantic (422); захисна перевірка також є перед Groq-викликом.

Приклад: {"description":"Так, є набряк","context":[{"role":"user","content":"Ударив ногу"},{"role":"assistant","content":"Чи є набряк?"}]}

Відповідь додатково містить follow_up_question (рядок до 300 або null) і context_used (true, якщо сервер передав непорожній контекст у AI-запит; це не оцінка правильності AI). Попередні чотири поля залишаються. Старі клієнти можуть їх ігнорувати; новий Android приймає стару відповідь для початкової перевірки, але для уточнення вимагає context_used=true. Без цього результат не додається в історію як уточнення.

Мобільний клієнт обмежує розмову трьома уточненнями; повтор після мережевої помилки надсилає той самий description і context. Для використання треба розгорнути ці зміни backend; Git push/deploy у цій задачі не виконувалися.

## 17.10.2026 — ЛР5 та X-Request-ID

Сценарій перенесено в AnalysisService з AIProvider; це зміна внутрішньої архітектури. Запити, шість полів успіху, HTTP 400/422/503/500 та disclaimer збережено. Domain errors централізовано обробляє main.py. Семантика description до/після strip не змінена цією задачею.

Кожна HTTP-відповідь містить **X-Request-ID**, включно з помилками валідації та неочікуваною 500. Це UUID hex, створений сервером; вхідний X-Request-ID ігнорується. Такий самий request_id міститься в серверних логах. JSON-поле request_id не додавалося, Android змін не потребує. ID призначений для пошуку помилки, не для автентифікації/ідемпотентності.

FakeProvider доступний лише за явного AI_PROVIDER=fake або DI override у тестах; успіх має позначку синтетичного demo. FAKE_PROVIDER_ERROR=true дає контрольовану 503. Немає автоматичної підміни Groq на fake.
