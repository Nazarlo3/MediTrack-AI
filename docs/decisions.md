# Архітектурні рішення MediTrack AI

Актуалізовано 17.10.2026 за робочим деревом. «Підтверджено кодом» описує реалізацію; пояснення вибору наведено тільки коли воно зафіксоване у попередніх рішеннях, планах або вимогах. Нові рекомендації не вважаються ухваленими.

## Інваріанти для наступних змін

- **API змінюється узгоджено.** [models.py](../backend/models.py), [SymptomModels.kt](../app/src/main/java/com/example/meditrackai/network/SymptomModels.kt) та обидва валідатори мають лишатися сумісними. Старі початкові відповіді без нових nullable-полів приймаються; уточнення потребує context_used=true. Додавання нової категорії вимагає змін обох наборів; їхню рівність перевіряє [backend-тест](../backend/tests/test_ai_service.py).
- **Немає вигаданого успішного fallback.** Невідома category → «інше», некоректна urgency/відповідь → помилка. Повна успішна відповідь записується як новий історичний результат; помилка локального запису не означає, що AI-запит не відбувся. [SymptomAnalysisController.submit](../app/src/main/java/com/example/meditrackai/ui/SymptomAnalysisController.kt).
- **Історія не перезапускає AI.** Деталі читаються за ID; видалення також за ID, навіть для однакових описів. Старі createdAt=null не замінюються датою міграції. Ліміт 20 — у [HistoryJsonCodec](../app/src/main/java/com/example/meditrackai/data/HistoryJsonCodec.kt).
- **Ліки v3 — по окремих прийомах.** takenDoseDates прив’язує дату до часу. Редагування зберігає ID і дати для незмінених часів, змінює scheduleVersion. URI/tag alarm містить ID+час; дія додатково перевіряє дату, версію й одноразовий токен. [План feature_9](impl/feature_9/plan.md), [DoseActionPolicy](../app/src/main/java/com/example/meditrackai/reminders/DoseActionPolicy.kt).
- **Відкладення лише у тій самій даті.** Останні 10 хвилин дня кнопка не показується, щоб не приписати вчорашній прийом новому дню; причина прямо зазначена у DoseActionPolicy. Прийоми інших часів не переносяться.
- **Контекст обмежений сесією.** До трьох уточнень, до шести попередніх повідомлень; кожна нова відповідь має окремий запис із користувацькими уточненнями. [План feature_10](impl/feature_10/plan.md), [SymptomViewModel](../app/src/main/java/com/example/meditrackai/ui/SymptomViewModel.kt). Причина вибору саме числових лімітів окремо не встановлена.
- **Перевірений commit перед публікацією стану даних.** LocalDataStore/ThemeSettings працюють на IO; фонові receiver-и використовують спільні Mutex. Оновлення ліків перечитує v3; історія залишається кешованою в екземплярі. Не поширювати гарантію відсутності втрачених оновлень на довільну кількість writer-ів.
- **Підпис release окремий.** [Gradle](../app/build.gradle.kts) читає локальний keystore.properties; без нього release не підписується, debug-ключ не підставляється. [README](../README.md) пояснює несумісність старого debug-підпису з release. Секретні файли/локальні матеріали виключені через [.gitignore](../.gitignore); це не аудит історії Git на секрети.

## Технічні борги та невирішені рішення

Підтверджені обмеження: спільний sticky readError для історії/ліків; немає інструмента відновлення пошкодженого сховища; delivered записується до notify (можливий пропуск при аварії); Python-залежності не закріплені; версії lifecycle-runtime і ViewModel Compose різні. Останнє — факт конфігурації, а не доведена несумісність.

Потребують окремого рішення, а не автоматичної реалізації:
1. Чи потрібні backup-виключення/шифрування, яка політика зберігання чутливих описів і фото. allowBackup=true й відсутність явних виключень не підтверджують фактичний хмарний backup на конкретному пристрої.
2. Як захищати публічний backend від стороннього використання; чи робити конфігуровану адресу/ключ. Клієнтський ключ у поточну архітектуру не входить.
3. Чи відновлювати незавершену AI-сесію/запити після завершення процесу; офлайн-черга ЛР4 — необов’язковий додатковий обсяг.
4. Чи поширювати repository/use case/DI зі сценарію аналізу на ліки; чи потрібні Room або відновлюване сховище. Для поточного сценарію ЛР5 цієї міграції не потрібно.
5. Який реліз/серверний deploy міститиме нові можливості, які перевірки потрібні для нього та як автоматизувати CI. Конфігурації CI/CD у репозиторії не знайдено.

Докладні факти — [architecture.md](architecture.md); розділення проблем і рекомендацій — [ROADMAP.md](ROADMAP.md).

## ЛР5 — прийняті рішення 17.10.2026

- Спочатку виконано **варіант Б** для backend, потім користувач погодив додатково **варіант А** для Android. Обидва охоплюють аналіз/уточнення, без повної Clean Architecture. [План](impl/feature_12/plan.md).
- AIProvider — стандартний Protocol, GroqProvider і FakeProvider — взаємозамінні реалізації. AnalysisService отримує провайдер через конструктор, HTTP-шар — через Depends. Окремий DI-фреймворк не потрібний.
- Незалежні dataclass та domain errors розміщені в одному domain.py для малого сценарію; Pydantic залишено в models.py з явними mapper-методами. Прикладна логіка не імпортує FastAPI/requests.
- Середовище/.env читає лише config.py, Settings кешуються на процес. Defaults зберігають поточну модель та 15-секундний timeout; ключ приховано з repr. Groq не підміняється fake при збої.
- Семантику довжини до strip збережено заради окремого контрольованого рефакторингу; вирівнювання з Android лишається окремим рішенням. Коди 400/422/503/500 і JSON збережені.
- Після успішного checkpoint додано request_id **у заголовок**, а не нове JSON-поле: Android-контракт не змінюється. Сервер генерує UUID, щоб не копіювати чутливий/довільний клієнтський рядок у логи. Немає логування опису чи сирого exception; компроміс — менше подробиць traceback, натомість ID і тип помилки.
- HTTPX додано лише до requirements-dev.txt для реальних HTTP-перевірок ASGI через TestClient. Runtime-залежності не змінено. Тести не використовують живого Groq; окремий ручний синтетичний виклик перевірено й записано в testing.md.

## ЛР5 — додатковий варіант А Android

- Domain-моделі й контракт SymptomRepository відділені від Gson/Retrofit. Причина: погоджена вимога ЛР5 і незалежні тести. Старі DTO залишено також моделями серіалізації, щоб не мігрувати дані.
- AnalyzeSymptomUseCase перевіряє вхід і будує результат сценарію; HTTP/IO/storage перетворюються на SymptomError у data-шарі, повідомлення — у SymptomUiState.
- Ручну DI обрано без нової бібліотеки; SymptomAnalysisController дає тестувати presentation-стани та cancellation з ін’єктованим scope. У застосунку це viewModelScope, тож життєвим циклом керує ViewModel.
- Контрольне розширення додано після checkpoint: скасування лише мережевого Loading; попередній результат/чернетка уточнення зберігаються. Новий analysisId відрізняє новий успіх від повернення до попереднього після скасування.
- Скасований запит не зберігається; початий після Success дисковий запис кнопкою не скасовується. Це зберігає окреме повідомлення про збій сховища без повторного AI-запиту.
- Ліки не переписувалися; нові runtime/test залежності не додавалися. Залишаються sticky readError та зберігання контексту лише в пам’яті. [План і межі](impl/feature_13/plan.md).
