# ЛР6 — тривалість та інтенсивність симптому

## Нове розширення 20.10.2026

Після перегляду відповідності методичці реалізовано окреме змістовне розширення поверх 0.3: необов'язкові тривалість 1–30 днів та інтенсивність 0–10. План, baseline і контрольний набір зафіксовані **до реалізації** у [feature_16](impl/feature_16/plan.md). Це саме новий код Android/backend/AI, а не лише документація попередньої функції.

Потік: поля Compose → ViewModel/controller → SymptomInput/use case → DTO/Retrofit → SymptomRequest → AnalysisService → build_user_message → GroqProvider → валідація результату → UI/історія. Старі description/context працюють без додаткових полів. Backend строго перевіряє цілі числа, зокрема зберігає intensity=0; строки/boolean/дроби не перетворюються автоматично. Користувацька самооцінка не є клінічною шкалою й не задає urgency автоматично.

AI отримує параметри окремим блоком, враховує їх у поясненні, повертає надані числа в перевірюваному форматі та не вигадує відсутні. Details_used підтверджує передачу, не правильність моделі; Android вимагає цей прапорець для нового сценарію. Початкові параметри збережені при retry/clarify та у тексті історії/контексті без зміни старої JSON-схеми. Чернетки rememberSaveable, loading/error/retry/cancel збережені. Пізніше текстове уточнення може виправити початкові відомості.

Критерії ДО реалізації: 5/5 спільних регресій, 5/5 нових сценаріїв (категорія, details_used та надані числа у фактичному explanation), 10/10 валідних результатів. Новий [набір](../backend/evaluation/details/README.md) порівнює **0.3 з 16 категоріями** та нову реалізацію при однакових моделі/temperature/max_tokens/timeout. П’ять спільних вводів дослівно повторені з 18.10; точні історичні вводи ЛР4 не відновлено. Основний приклад ушкодження — однозначний удар гомілкою об ліжко; монітор залишено лише в старих доказах.

Живий результат 20.10: baseline 5/5 регресій і 0/5 нових очікувань, current 5/5 + 5/5; по 10/10 валідних відповідей. Усі 20 запитів отримали 200 з першої спроби, повторів немає. Це демонстрація підтримки параметрів, не 100% медична точність. [Повні протоколи](../backend/evaluation/details/results/SUMMARY.md). Локальні перевірки: 38 backend tests OK, 61 Android unit tests без помилок, debug/test APK зібрані.

Новий телефонний сценарій — **OK (1 test), 11.814 с**, з першого запуску. Xiaomi/Android 15, актуальний debug 0.3/code 3 → локальний FastAPI → Groq. Підтверджено блокування 31 дня, поля 3/5, числа у живому поясненні, details_used/context_used, уточнення та два незалежні записи/деталі історії. 65 користувацьких prefs незмінні, тестових prefs немає; перевірена приватна копія збережена локально. Сервер/reverse прибрано. [Мобільний протокол](../backend/evaluation/details/results/mobile.json). Один придатний новий PNG використано у звіті; знімок діалогу технічно некоректний і виключений. Фінальне Git-оформлення й свіжі локальні перевірки — [feature_21](impl/feature_21/changelog.md). Push/Render deploy та публікацію нового APK не виконували.

## Історичний етап 18.10.2026

Нижче збережено опис попереднього оцінювання. Воно не є основним доказом нового розширення ЛР6 й не замінює реалізацію вище.

### Попереднє завдання й межі

Варіант А: розширення попередньої категоризації. Користь — окремі категорії замість надто загального «інше» та можливість уточнити опис у поточній перевірці. Розширення вже є у вихідній 0.3; ЛР6 додає відтворюване порівняння й докази, а не видає його за щойно написану функцію.

Вхід: опис 3–500 символів та необов'язкові до трьох попередніх пар user/assistant, до 1500 символів у повідомленні. Вихід: категорія, пояснення, urgency, disclaimer, необов'язкове питання та context_used. Контекстний прапорець підтверджує передачу, а не правильне розуміння AI. Діагноз, лікування, confidence та клінічна точність не входять у завдання.

## Порівняння та критерії (до запуску)

Baseline — SYSTEM_PROMPT і 7 категорій з коміту `13cea78`, max_tokens=200, без контексту. Current — SYSTEM_PROMPT з вихідного `c1eff7f`, 16 категорій, max_tokens=400, з контекстом. Обидва викликаються зараз через однаковий транспорт Groq, ту саму налаштовану модель, temperature=0.1, JSON mode, timeout. Це порівняння конфігурацій AI, не двох повних APK/серверів; змінено кілька чинників, тому причинність окремого правила не доводиться.

Точні п'ять вводів старої ЛР4 не збережено. `cases.json` містить новий фіксований синтетичний набір: п'ять регресій старих категорій; три нові категорії/механізм травми; два уточнення з вручну заданими попередніми повідомленнями. Вигадані репліки assistant позначено як тестові, вони не є відповідями моделі.

Пороги для current: **5/5** регресій, **3/3** розширення, **2/2** контексту, **10/10** структурно валідних результатів без транспортних помилок. Збіг категорії — основна метрика; обмежені перевірки urgency/question застосовуються лише де явно задані в cases. Поріг baseline не є умовою приймання: відсутня нова категорія/контекст — вимірюване обмеження старої версії.

Це інженерні мітки відповідності заявленому сценарію, не медичний еталон. Один запуск не є статистичною оцінкою, температура 0.1 не гарантує ідентичності відповідей. Невиконаний поріг потрібно записати, а не виправляти мітки після отримання відповідей.

## Реалізація

`AnalysisService` (`backend/analysis_service.py`) перевіряє/готує вхід; `GroqProvider` (`backend/ai_service.py`) формує messages і викликає AI; `_validate_ai_result` перевіряє результат. `main.py`/`models.py` — HTTP boundary. `SymptomAnalysisController` → `AnalyzeSymptomUseCase` → `SymptomRepository` — мобільний потік, UI — `SymptomCheckScreen.kt`. API не змінюється.

Набір і запуск: [backend/evaluation](../backend/evaluation/README.md). Помилки HTTP/timeout/формату не стають успішним «звичайне»; автоматичної підміни Groq на fake немає. На телефоні мають зберігатися loading/success/error/retry/cancel, історія й старий початковий запит. Попередні перевірки ЛР5 не замінюють новий контроль ЛР6.

## Докази й відтворюваність

Конфігурації містять точний промпт, його SHA-256 і Git provenance. Результат runner містить час, Git HEAD, Python/версії пакетів, ідентифікатор моделі у запиті та відповіді, параметри, вхід, відповіді й усі спроби. Ключі/заголовки та `.env` не записуються. Не слід запускати набір з реальними медичними даними. Увесь набір — 20 запитів без автоматичних повторів; невдалий запуск зберігається окремо.

## Результат 18.10.2026

[Повна таблиця та два JSON-протоколи](../backend/evaluation/results/SUMMARY.md). Після явного повтору лише транспортно невдалих рядків: baseline 6/10 очікувань, current 10/10 (5/5 + 3/3 + 2/2). Поточні 10 відповідей структурно валідні. На першому прогоні було сім 429: baseline отримав 9/10, current 4/10 валідних відповідей. Отже, початкова умова без транспортних помилок **не виконана**; успіх після повторів показує відповідність сценаріям, а не гарантовану доступність.

Семантично невдалі відповіді baseline не повторювалися; набору/міток/промптів за відповідями не підганяли. Runtime-код AI, API й Android у ЛР6 не змінювалися: додаткове виправлення функції не знадобилося. У runner додано окреме явне продовження після 429 зі збереженням усіх спроб і паузою 12 с за замовчуванням.

Новий мобільний сценарій `Lab5PhoneScenarioTest.lab6InjuryClarificationChangesCategoryWithoutRewritingHistory` пройшов на Xiaomi/Android 15: **OK (1 test), 9.16 с**. Початковий опис можливого удару дав «травми та ушкодження»/«увага» і питання; заперечення травми — «інше»/«звичайне», context_used=true. Два різні результати перечитано зі сховища, початковий не перезаписаний. Два нові PNG переглянуто й збережено локально в `docs/various files/screenshot/ЛР6`.

До успіху збережені два невдалі запуски: NETWORK через втрачений після перепідключення ADB reverse; потім помилка самого тесту (порівняння DTO/domain), виправлена через mapper. Оновлювався тільки test APK; встановлений debug-застосунок має versionName 0.2/code 2, release 0.3 на телефоні цим прогоном не перевіряли. 65 користувацьких SharedPreferences незмінні за SHA-256, тестових prefs не залишилося. Локальний сервер зупинено, тестовий reverse прибрано. [Мобільні протоколи](../backend/evaluation/results/mobile.json).

Історичне обмеження методики: критерії записано до цього оцінювання, але до реалізації розширення у попередніх роботах їх не фіксували. Нові синтетичні вводи й поточна перевірка не відновлюють відсутні історичні докази.
