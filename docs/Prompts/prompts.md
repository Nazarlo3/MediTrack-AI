# Збережені промпти (Лабораторна робота 3)

Файл містить шість промптів для coding agent (Gemini в Android Studio) і опис результату кожного. Перші п'ять промптів підготовлено за допомогою Claude; промпт тестування №6 — за допомогою Codex. Ключі та персональні дані в промптах відсутні. Старі результати описують стан на момент відповідного запиту, а не фінальний стан проєкту.

## 1. Аналіз

**Промпт:**

```
Повністю перегляньте код усього проєкту MediTrack AI: Android-застосунок (app/), backend (backend/), документацію (docs/), README, build-файли, .gitignore і git-стан. ПОКИ НІЧОГО НЕ ЗМІНЮЙ: не редагуй файли, не роби git add, commit, checkout, restore, reset чи stash. Лише читання й аналіз.

Перевір:
1. Безпека: секрети, API-ключі, .env у репозиторії або в історії git, хардкоджені адреси, зайві Android permissions, логування чутливих даних, показ технічних деталей помилок користувачу.
2. Backend: помилки валідації, обробка збоїв Groq, відповідність моделей Pydantic і JSON, що повертає /analyze-symptom, залежності в requirements.txt.
3. Mobile: відповідність моделей SymptomModels.kt відповіді backend, обробка помилок у SymptomViewModel, помилки в корутинах, ризики в MedicationSection (збереження URI фото), робота з SharedPreferences.
4. Узгодженість: чи однакові категорії й рівні терміновості в backend і mobile, чи збігаються назви полів API, чи не розходиться документація з кодом.
5. Git: незакомічені зміни, untracked-файли, що не можна комітити (наприклад .idea/), історія комітів.
6. Документація: чи відповідають docs/ і README фактичному коду. Назви конкретні розбіжності.
7. Тести: що реально існує і що запускається.

Формат: короткий висновок (3-5 головних проблем), таблиця (проблема | де | серйозність | що зробити), окремо список того, що вже добре, і порядок виправлень. Для кожного пункту показуй доказ із коду. Не вигадуй проблем, яких немає.
```

**Результат:** агент знайшов проблему з тимчасовими `content://` URI фото ліків, відсутність фіксованих версій у `requirements.txt`, зайвий `.idea/` у git і розбіжність таймауту в README (30 с проти 60 с у коді).

**Що перевірено:** частину висновків агента (версії в `requirements.txt` та приклади версій) я звірив і виправив: версії треба брати з `pip freeze`, а не вигадувати.

## 2. План

**Промпт:**

```
Задача: виправити зникнення фото ліків після перезапуску застосунку.

Спочатку НЕ пиши жодного коду і не змінюй жодних файлів. Зроби тільки аналіз і план.

Крок 1. Прочитай код, який стосується фото ліків і збереження даних. Знайди сам: де вибирається фото, де зберігаються ліки (SharedPreferences), як читається фото при показі, як видаляються ліки. Використовуй реальні шляхи з проєкту, нічого не вигадуй.
Крок 2. Перевір, чи проблема справді в тому, що зберігається тимчасовий content:// URI. Покажи мені фрагмент коду, який це доводить.
Крок 3. Створи файл docs/impl/feature_3/plan.md: причина з доказом, запропоновані зміни по файлах, файли які НЕ чіпатимеш, нові залежності, як перевірити вручну, ризики.
Крок 4. Створи docs/impl/feature_3/changelog.md з порожнім шаблоном.
Крок 5. ЗУПИНИСЬ. Напиши: «План готовий, чекаю підтвердження». Не пиши код і не роби git-команд, що змінюють стан.

Після мого «план затверджую» виконай план тільки для файлів з плану. Не рефактори інше. Збери :app:assembleDebug і :app:assembleRelease і покажи git diff.
```

**Результат:** агент склав план у `docs/impl/feature_3/plan.md` і зупинився до коду. Перша версія плану містила фрагмент Logcat, якого в моєму реальному логу не було. Я його не затвердив і зажадав доказ.

**Що перевірено:** номери рядків у плані та відповідність фрагмента реальному логу.

Зроби тільки діагностику: DiagnosticLog з lastError у loadSampledBitmapFromUri, червоний текст під назвою ліків і кнопку «Скопіювати діагностику». Більше нічого не міняй. Збери :app:assembleDebug і зупинись. Чекай, поки я відтворю проблему і скину текст помилки.

## 6. Тестування

Дата внесення результату: 13.10.2026. Перевірка наявної реалізації без зміни коду. Збережена відповідь: [Відповідь джемені_1.txt](../various%20files/Відповідь%20джемені_1.txt).

**Промпт, підготовлений для надсилання Gemini:**

```text
Перевір проєкт MediTrackAI: нову функцію оцінки терміновості симптомів і збереження попереднього сценарію аналізу.

На цьому етапі лише читання та запуск перевірок. Не редагуй код, документацію чи конфігурацію. Не виконуй git add, commit, reset, restore, checkout або stash. Створення звичайних build/test-звітів дозволене. Не показуй вміст .env та секрети.

1. Прочитай docs/ai-instructions.md, docs/testing.md, docs/api-contract.md та релевантний код Android і backend.
2. Перевір узгодженість моделей запиту/відповіді, дозволених значень urgency та їх відображення в Android.
3. Переглянь наявні тести. Поясни, що вони перевіряють, а що не покривають.
4. Запусти з кореня проєкту:
   .\gradlew.bat :app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleRelease
   Якщо запуск неможливий — наведи фактичну причину. Не видавай невиконану команду за успішну.
5. Перевір по коду сценарії:
   - коректний опис симптому;
   - порожній ввід і самі пробіли;
   - довжина 2, 3, 500 і 501 символ;
   - три рівні urgency;
   - відсутність інтернету та повторна спроба;
   - сумісність попереднього запиту лише з description.
   Аналіз коду не називай ручним або інтеграційним тестуванням.
6. Переглянь git diff на випадкові зміни та можливі секрети, не виводячи самі секрети.
7. Запропонуй мінімальні додаткові тести для нової та попередньої поведінки, якщо покриття недостатнє. Поки їх не додавай.

Відповідь українською:
- виконані команди та фактичні результати;
- перевірка | спосіб перевірки | результат | доказ;
- знайдені проблеми;
- що лишилося перевірити на телефоні;
- які тести пропонуєш додати.

Не вигадуй логи, результати AI чи перевірки на пристрої. Наприкінці зупинись і чекай підтвердження перед змінами.

Додатково перевір feature_6 за docs/impl/feature_6/plan.md та changelog.md: обчислення графіка, системні дозволи, скасування й відновлення нагадувань, наявні тести.

Користувач підтвердив на телефоні: production-нагадування надійшло, коли застосунок був згорнутий. Це повідомлений користувачем результат, а не перевірка агента. Перезавантаження телефона, відмови в дозволах і решту сценаріїв не вважай перевіреними.
```

Збережено текст підготовленого промпту та доповнення з листування. Окремого експорту фактичного вхідного повідомлення Gemini немає; надана користувачем відповідь охоплює ці завдання, включно з feature_6.

**Результат за відповіддю Gemini:**

- Повідомив про успішний запуск unit-тестів, lint, debug/release (`BUILD SUCCESSFUL in 11s`) після налаштування JDK Android Studio й усунення конфлікту `ANDROID_PREFS_ROOT`/`ANDROID_USER_HOME` у процесі термінала. Окремий сирий лог цього запуску не наданий.
- Порахував 10 змістовних тестів: 3 у `FormValidatorsTest`, 7 у `MedicationScheduleTest`. Lint: 0 помилок, 41 попередження.
- Проаналізував моделі API, urgency, валідацію, retry, графік і системні дозволи; більшість сценаріїв перевіряв читанням коду, а не запуском на телефоні чи зверненням до реального AI.
- Вказав на відсутність окремих автоматичних тестів ViewModel, LocalDataStore та backend; запропонував їх, але не додавав.
- Залишив ручні сценарії reboot, дозволів, двох препаратів, часового поясу та release непідтвердженими. Користувацьку перевірку одного повідомлення у згорнутому стані відокремив від власних перевірок.

**Що звірив Codex та які уточнення потрібні:**

1. Наявні XML-звіти містять 11 тестів загалом: 10 змістовних та 1 шаблонний `ExampleUnitTest`; усі без помилок/пропусків. Їхні часові позначки — 12.10.2026 UTC: це підтверджує наявний результат, але не доводить повторне виконання тестів замість використання Gradle-кешу під час запуску Gemini.
2. Валідація Android перевіряє довжину після trim, backend Pydantic — до strip. Межі 3–500 однакові, але поведінка для короткого тексту з пробільним доповненням не цілком тотожна. Запит лише з `description` узгоджений; формат локального сховища не є доказом сумісності API.
3. Різні препарати мають однаковий requestCode `0`, але різні Intent URI з повним ID, тому alarm розрізняються. Формулювання Gemini «різні ID PendingIntent» потребує цього уточнення.
4. Через поточну форму не можна додати минулу дату або рядок часу без `HH:mm`: валідація їх блокує. Перевірка старих/прострочених записів потребує підготовлених тестових даних або очікування завершення курсу; не слід змінювати реальні дані заради тесту.
5. Висновок Gemini про відсутність секретів — результат описаного ним огляду, а не доказ повного аудиту всіх файлів та історії Git. Тексти секретів у наданій відповіді відсутні.
6. Статуси «успішно» для аналізу коду означають відповідність прочитаної реалізації, а не проходження всіх сценаріїв на пристрої. Додаткових тестів чи змін коду за цією відповіддю не виконувалося.
