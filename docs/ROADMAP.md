# Стан і наступні кроки MediTrack AI

Актуально на 04.11.2026. Код: 0.4 та локальна інтеграція ЛР7. Реліз 0.4 опублікований; ЛР7 не змінює його автоматично. [Архітектура](architecture.md), [новий протокол](impl/feature_22/verification.md).

## Реалізовано

- Android Compose → ViewModel/controller → use case/repository → Retrofit; FastAPI → AnalysisService → AIProvider/GroqProvider, ручна DI/Depends, типізовані помилки й X-Request-ID.
- 16 категорій, 3 рівні urgency, до трьох уточнень, скасування/повтор; необов’язкові тривалість 1–30 та інтенсивність 0–10. Джерела: SymptomModels.kt, AnalyzeSymptomUseCase.kt, backend/models.py та ai_service.py.
- ЛР7: has_usable_result=false → окремий NoResult, пояснення/питання, без запису завершеного аналізу. Старі відповіді сумісні. Debug URL задається Gradle property; release URL збережено.
- Історія до 20 записів, деталі, міграція, видалення одного/всіх із підтвердженням; LocalDataStore/HistoryJsonCodec.
- Ліки з фото/редагуванням, до 12 часів, статус кожного прийому за датою, alarm, відкладення на 10 хв, дії сповіщень, системна/світла/темна тема. Джерела: MedicationSection, MedicationJsonCodec, reminders/.
- ЛР7: 64 Android unit-тести, 42 backend-тести; debug/test APK, lint 0 errors/43 warnings. Підтверджені 10 функціональних сценаріїв, 10 AI-прикладів (8 валідних, 2 невалідні); невдалі перші спроби не приховані. Деталі/межі — протокол.

## Підтверджені відкриті задачі

1. F07 пройдено 05.11.2026 після ручної відмови у сповіщеннях. Дозвіл повернуто й перевірено; дані збережені.
2. Фінальне Git-оформлення ЛР7: відібрати лише її зміни, створити фінальний commit/тег і зв’язати з APK. Сторонні ЛР2–3 та локальні файли виключити.
3. Довжина description: backend перевіряє до strip, Android після trim. Зміна контракту нормалізації потребує окремого рішення; не є виправленням ЛР7.
4. Last request/AI-контекст не переживають завершення процесу; пошкодження сховища блокує запис без автоматичного відновлення. Немає офлайн-черги, синхронізації, адреси/API-ключа в UI.
5. Runtime Python-залежності не закріплені, CI не заданий; немає backend auth/rate limit, окремого шифрування чи backup-виключень. Це технічні обмеження, не доказ експлуатації.

## Рекомендації за пріоритетом

Це рекомендації, не автоматично погоджені нові функції.

- P1: завершити Git і особисто повторити захисну демонстрацію за README. Нове розгортання/реліз — за окремим дозволом.
- P1: визначити політику захисту даних/backup/cleartext та доступу до публічного API; узгодити нормалізацію description.
- P2: закріпити Python-середовище й налаштувати CI; розширити AI-набір, враховуючи зовнішні збої. Мале інженерне оцінювання не є медичною валідацією.
- P2: перевірити reboot, наступний день, зміну поясу/реальні відкладені нагадування, process death та новий release на телефоні. Наявність коду не замінює перевірку пристрою.
- P3: за потреби поширити repository/use case на ліки та ізолювати помилки сховищ. Room не є обов’язковою зміною.

## Після ЛР7: feature_23 (05.11.2026)

Реалізовано в локальному коді: добровільне серверне збереження нового запиту/відповіді, перемикач/перший діалог, видалення записів встановлення, захищений JSON-перегляд і статистика, строк 90 днів. Дані не навчають модель автоматично. Нові контрольні перевірки — feature_23, не історичний набір ЛР7.

Відкрито перед хмарним використанням: постійний приватний диск/БД, секрет адміністратора, правила резервних копій/видалення, розгортання за окремим запитом. Наступні можливі покращення — rate limiting/auth і централізована БД для кількох інстансів. [Операторська інструкція](data-collection.md).
