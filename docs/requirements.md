# Requirements — MediTrack AI

## Реалізовані вимоги
1. **Мобільний UI (Android / Jetpack Compose):**
   - Початкова вкладка «Мої ліки» при запуску без відновленого стану.
   - Текстове поле для вводу симптому: 3–500 символів після обрізання крайніх пробілів; порожній ввід блокується.
   - Відображення станів `Idle`, `Loading`, `Success`, `Error`.
   - Інформаційна підказка про холодний старт хмарного сервера під час завантаження.
   - Можливість повторного запиту при помилці без перезапуску застосунку.

2. **Backend API (FastAPI / Python):**
   - Ендпоінт `GET /health` для перевірки статусу.
   - Ендпоінт `POST /analyze-symptom` з валідацією Pydantic (`min_length=3`, `max_length=500`).
   - Помилки `422` для валідації Pydantic, `400` для опису лише з пробілів, `503` для контрольованих збоїв AI; загальний обробник неочікуваних помилок повертає `500` без stack trace у відповіді.

3. **AI-Інтеграція (Groq API):**
   - Використання моделі `qwen/qwen3.8-27b`.
   - Запит формату `json_object` із полями `category`, `explanation`, `urgency`; перевірка й нормалізація результату на backend.

## Реалізовані розширення
- Оцінка рівня терміновості з кольоровим кодуванням картки.
- Локальна історія до 20 перевірок симптомів.
- Список препаратів із позначкою прийому за датою.
- Локальні нагадування за часом, днями тижня та кінцевою датою; відновлення після перезавантаження, скасування після видалення/прийому сьогодні, доступ до дозволів у звичайному UI. Користувач підтвердив доставку при згорнутому застосунку та два повідомлення на однаковий час. Окремість перевірок прийому/видалення, reboot, наступний день, відмови в дозволах і release на телефоні ще не підтверджені.

## Незавершені функції
- Кілька часів прийому одного препарату за день та відкладення нагадування.
- Тривалість симптому у днях: описана лише в експериментальних планах, не є реалізованою функцією.

## Критерії готовності (Definition of Done)
- Код успішно компілюється в Android Studio без помилок.
- Backend відповідає на розгорнутому у хмарі сервері Render.
- Всі сценарії обробки помилок відпрацьовують стабільно без аварійних завершень (crashes).

Це критерії приймання, а не твердження, що всі перевірки вже виконано. Фактичний статус наведено в [testing.md](testing.md).
