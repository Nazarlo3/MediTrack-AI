# Збір звернень для покращення AI

## 0.5.1 — стійка черга й безкоштовний Render

`COLLECTION_OUTBOX_PATH` вмикає SQLite outbox для Google. Це має бути приватний **постійний** диск (наприклад `/var/data/meditrack/outbox.sqlite3` на вже підключеному диску), не каталог репозиторію/тимчасова файловa система. Локально можна задати абсолютний шлях у `backend/private-data/`; ця папка виключена з Git. Значення `:memory:` у production Settings заборонене. Нових залежностей немає.

Задача фіксується до queued; ack видаляє її тільки після відповіді Google. Зберігаються payload і SHA-256 власника без сирого capability. Максимум 64 задачі, строк 24 години; очищення при операціях/запуску writer, після зупинки сервера — після наступного запуску. `secure_delete`/`synchronous=FULL`, приватні права нових файлів; окремого шифрування SQLite немає. Оператор визначає шифрування диска/backup і не додає БД у Git. У Google — попередні 90 днів та обмеження історії версій.

При тимчасовому збої паузи 2/4 с, після третьої невдачі — 15 хв до завершення строку. Постійна 4xx/неочікувана помилка лишає failed-задачу до строку для перевірки оператором; не видається за успіх і не повторюється щосекунди. Повтор після падіння між Google-записом та ack дедуплікується. Видалення спочатку фіксує локальне відкликання й прибирає payload, потім видаляє Google-рядки; при збої Google повертається помилка, повтор видалення потрібний.

Без outbox path використовується прямий синхронний запис: немає прийнятих RAM-задач, saved лише після Google. Якщо шлях налаштовано, але диск/БД недоступні, збір повертає unavailable, а видалення — 503, без обходу локальних відкликань і без скидання БД. AI-результат залишається доступним. У синхронному режимі Google-виклик може затримати HTTP-відповідь; майбутнє завантаження непідтверджених записів не гарантується.

Read-only перевірка Render підтвердила free/no disk. Стійкість SQLite там не заявляється; постійний диск/зовнішня БД потребують окремого рішення. Старі описи RAM-черги нижче — попередня реалізація feature_25.

## Feature_25 — поточний локальний код

UI та ViewModel тепер користуються одним графом залежностей Application; DataCollectionSettings додатково читає фактичний збережений enabled перед кожним запитом і синхронізує екземпляри через listener. Вимкнення стосується наступних запитів, не відкликає вже відправлене.

Google-записи приймає черга CollectionDispatcher: до 64 поточних/очікуваних задач, один writer, максимум 3 спроби з паузами 2/4 с для мережевих, 401/408/429/5xx помилок. Повтор із тим самим UUID/власником дедуплікується адаптером. AI не чекає Google. `queued` не означає `saved`; окремого клієнтського підтвердження завершення черги немає. Після вичерпання спроб — загальне попередження без текстів/ключів у серверному журналі. Черга лише в RAM: рестарт/примусова зупинка може втратити задачі; завершення процесу дає до 5 с на best-effort drain. Стійка черга потребує окремого постійного сховища. SQLite залишається синхронним.

Невідомі DELETE більше не наповнюють реєстр відкликань. Прийняті до AI/черги запити враховуються при видаленні, щоб пізній запис залишався заблокованим. Публічні операції мають ліміти — [API](api-contract.md). Це зміни локального коду, не нова перевірка хмари. Раніші розділи нижче описують історичні етапи.

Стан розгортання: Google-збереження на Render активоване й перевірене реальним синтетичним AI-запитом та власним видаленням. [Доказ](impl/deploy_sheets/verification.json). Старі статуси «ще не розгорнуто» нижче описують попередні етапи.

## Поточна поведінка налаштувань (уточнено користувачем)

Збір нових звернень початково ввімкнений. Окремого діалогу/підтвердження при запуску немає. Перемикач і розгортані подробиці «Покращення AI» знаходяться лише в налаштуваннях. Раніше збережене вимкнення не скидається. Кнопку видалення серверних записів прибрано з UI; серверний DELETE збережено для керованих операцій/тестів. Вимкнення зупиняє нове збереження, але не видаляє раніше записане.

Поле consent_version=2 у сумісному протоколі означає підтримувану версію повідомлення/режиму, а не доказ явної згоди користувача. Раніші розділи про обов’язковий перший діалог описують попередню ітерацію і не відповідають поточному Android. Повідомлення в подробицях називає приватну Google-таблицю, вміст/мету збору, доступ адміністратора, строк і Google-історію версій.


## Google Sheets — актуальний режим (09.11.2026)

Google Sheets тепер підтримується як основне сховище. Нижчеописаний SQLite — альтернативний локальний режим попереднього етапу. Наявність GOOGLE_SHEETS_ID обирає Google без прихованого fallback на SQLite. Потрібні GOOGLE_APPLICATION_CREDENTIALS (шлях приватного JSON-ключа) і google-auth[requests] із requirements.txt. COLLECTION_ADMIN_TOKEN залишається окремим секретом для admin API; його не записують у таблицю. Всі Android API/DELETE лишаються ті самі.

У Google створюються «Звернення», «Статистика» і прихований _MediTrack_keys. Наявні інші аркуші збережені. Тексти передаються як stringValue, ніколи не як формули. Статистика — актуальний snapshot, який backend оновлює атомарно разом із записом/видаленням/очищенням. Приховування службових колонок/аркуша не є захистом: будь-який редактор таблиці може їх відкрити. Доступ надавати лише власнику та service account.

Поточний Android надсилає версію повідомлення 2; Google Sheets, доступ адміністратора й межі очищення описані у подробицях налаштувань, без початкового діалогу. Старі Android-клієнти з версією 1 не включають Google-збір, отримують X-Collection-Status=consent_required. Збережене «вимкнено» не скидається. SQLite сумісний із версіями 1/2, записує фактичну версію.

90 днів — строк доступності поточних рядків; сервер видаляє їх при операціях та щогодини під час роботи. Історія версій/копії Google можуть зберігати минулі дані; видалення рядків не гарантує їх фізичного стирання у Google. Модель автоматично не навчається. Автоматичної міграції/очищення старого SQLite при перемиканні немає: за наявності старих даних оператор має врахувати обидва сховища.

### Конфігурація й обмеження

```text
GOOGLE_SHEETS_ID=<ID приватної таблиці>
GOOGLE_APPLICATION_CREDENTIALS=<абсолютний шлях серверного secret file>
GOOGLE_HTTP_TRANSPORT=requests
```

requests — типовий транспорт для сервера; curl — додатковий режим для середовищ із повільним DNS у Python, вимагає curl у PATH. В обох випадках TLS перевіряється; токен тільки в заголовку, не URL/логах. У curl секретні заголовки й тіла передаються виключно через stdin, не аргументи процесу чи тимчасові файли. Бібліотека google-auth потрібна для підписання й OAuth. На локальному ПК налаштовано ігнорований backend/.env з наданим ID, шляхом ключа й curl, решту параметрів збережено.

Запуск із backend/: `python -m uvicorn main:app --host 127.0.0.1 --port 18765 --workers 1 --no-access-log`. Уже запущений старий сервер потрібно перезапустити, щоб підхопити новий код і середовище. Google-інтеграцію вже розгорнуто раніше; нові зміни feature_25 поки локальні. Для розгортання потрібні secret file/змінні, requirements і рівно один worker/один інстанс для цього адаптера.

Це сховище для невеликої вибірки: до 10 000 поточних звернень і 10 000 відкликаних ключів. Ліміт реєстру ключів блокує новий збір, але не видалення. При перевищенні кількості звернень або зміні схеми — fail closed, без мовчазного пропуску строків чи чужих записів. Google має квоти; обмежена черга/повтори feature_25 описані вище. Не сортувати/переставляти/видаляти керовані рядки вручну під час роботи backend, не запускати кілька інстансів: блокування процесу не є розподіленою транзакцією. Для масштабування потрібна транзакційна БД. Операторське видалення ключового реєстру може порушити захист від пізніх записів.

59 backend-тестів пройшли, окремо реальний Google API із синтетичним FakeProvider: запис/читання/статистика/дублі/власне видалення/пізній запис. Тестові тексти прибрано, лише хеші відкликаних тестових ключів лишаються службовими. Це не живий наскрізний Android/Groq/Render-тест. Докладно — [feature_24](impl/feature_24/verification.md).


Реалізація feature_23, 05.11.2026. Це матеріал для ручного аналізу якості та статистики; автоматичного навчання Groq немає.

## Вибір користувача

У MainActivity використовується спільний DataCollectionSettings із repository. Початковий перемикач увімкнений, але noticeVersion ще 0: до явного вибору не надсилаються ні метадані збору, ні ключ. Перший діалог описує доступ адміністратора, вміст і строк та пропонує «Без збору даних». У налаштуваннях є перемикач і підтверджуване видалення. Локальна історія незалежна.

Увімкнення стосується нових запитів. Вимкнення не відкликає вже розпочатий запит і не видаляє минулі записи; для цього є окрема кнопка. Під час видалення збір спочатку вимикається. Сервер атомарно видаляє записи та відкликає ключ: пізня відповідь запиту з тим самим ключем не створить запис заново. Після підтвердження клієнт прибирає старий ключ; наступне добровільне ввімкнення створить новий. При помилці ключ зберігається для повтору видалення.

Ключ — 32 випадкові байти, hex, у приватних SharedPreferences. Не показується в UI/логах; передається X-Collection-Token. У БД тільки SHA-256. Preferences збору виключені з Android backup/device transfer. Після видалення застосунку/даних ключ може бути втрачено: видалити записи попереднього встановлення через нове встановлення неможливо. Це ідентифікація встановлення, не облікового запису; називати записи анонімними не можна.

## Вміст і строк

SQLite: поточний description, duration_days, intensity; повний типізований SymptomResponse (включно з NoResult), request UUID, час UTC, модель, тривалість AI-виклику в мс, consent version. Raw context, IP, ліки, імена/телефони окремими полями не збираються. Сам текст та відповідь можуть містити персональні дані, зокрема повторені моделлю деталі контексту; автоматичної гарантованої деідентифікації немає. Стара локальна історія не завантажується. Невалідні й технічно невдалі аналізи не записуються.

Записи старші 90 днів недоступні та очищуються під час читання/запису; lifespan FastAPI додатково запускає cleanup на старті та щогодини. Якщо сервер вимкнений, фізичне очищення відбудеться після запуску. SQLite secure_delete увімкнений. Це не стирання копій на файловій системі чи резервних копій. Tombstone-хеші відкликаних випадкових ключів без текстів зберігаються для блокування пізніх/повторних записів. Статистика враховує лише доступні, добровільно збережені успішні відповіді, не всіх користувачів і не всі помилки.

## Запуск оператором

За замовчуванням COLLECTION_DB_PATH порожній — збереження вимкнене. Схема створюється ліниво. Нових Python-залежностей немає. У власному серверному .env або середовищі задайте:

```text
COLLECTION_DB_PATH=<абсолютний шлях до приватного постійного диска>/collection.sqlite3
COLLECTION_ADMIN_TOKEN=<окремий криптографічно випадковий секрет щонайменше 32 символи>
```

Не використовуйте GROQ_API_KEY як адміністративний секрет. Не додавайте реальні значення до Git/Android. Для локальної перевірки допустима ігнорована backend/private-data/collection.sqlite3; шлях обчислюйте від робочого каталогу uvicorn. Усі HTTP-запити з ключами у хмарі мають іти через HTTPS. Локальний HTTP/adb reverse призначений лише для приватної демонстрації.

На хмарі до активації визначити постійність диска та резервних копій, обмеження доступу, шифрування диска, оператора і процедуру видалення. SQLite не має вбудованого в цій реалізації шифрування. Копіювати БД/експорти у Git заборонено. `.gitignore` виключає private-data та *.sqlite3/журнали. Поточні налаштування хмарного диска не перевірені; Render не оновлювався. Для кількох інстансів потрібне окреме рішення про централізовану БД; цей варіант призначений для одного сервера зі спільним локальним файлом.

## Перегляд і видалення

- `GET /collection/admin/records?limit=50&offset=0` — поточна сторінка, максимум 100. Повертає текст/відповідь без ключа чи owner hash.
- `GET /collection/admin/stats` — total, by_day (UTC), by_category, by_urgency, average_elapsed_ms. Це серверний час аналізу до запису БД, без мобільної мережі.
- Обидва GET вимагають `Authorization: Bearer <COLLECTION_ADMIN_TOKEN>`, не ключ встановлення. Без належного адміністративного секрету — 401. Короткий/відсутній секрет не відкриває доступ.
- `DELETE /collection/mine` з X-Collection-Token — видалення тільки власника цього ключа та відкликання ключа, без доступу до чужих записів. Налаштована БД потрібна навіть якщо видалення повторне.
- `Cache-Control: no-store` для відповідей із даними. Ключі передавати у заголовках, ніколи в URL.

Наприклад, у власному PowerShell із заздалегідь заданими серверною адресою й адміністративним секретом:

```powershell
$collectionHeaders = @{ Authorization = "Bearer $env:COLLECTION_ADMIN_TOKEN" }
Invoke-RestMethod "$env:MEDITRACK_SERVER/collection/admin/stats" -Headers $collectionHeaders
```

MEDITRACK_SERVER — адреса backend без кінцевого слеша. Не експортуйте тексти у публічні файли. Вбудованої адміністративної вебсторінки немає; доступ — JSON API.

## Сумісність і межі

Старий Android/клієнт не передає collection — жодного запису. Старий backend може ігнорувати метадані: Android показує відсутність підтвердження збереження. Відповідь аналізу не змінена; статус збору окремо у X-Collection-Status: not_requested, saved, disabled, rejected, revoked, unavailable. Помилка запису не ламає аналіз і не створює локальну чергу повторних завантажень. Повтор одного request UUID з тим самим власником не дублює рядок. Новий окремий AI-запит має новий UUID.

Не реалізовано auth користувачів, обмеження частоти публічного AI/DELETE, клінічну валідацію або автоматичне навчання. Власник ключа може підробляти звернення: статистика не є незалежно перевіреною вибіркою. Адміністратор має доступ до чутливих текстів; процедура експорту/резервних копій та розміщення перед production — відповідальність оператора.
