# Порівняння планів: без docs/ та з docs/

## Матеріали та умови

Порівнюються збережені [план без docs](plan_без_docs.md) і [план з docs](plan_з_docs.md) для однієї задачі: необов'язкова тривалість симптому 1–30 днів. Оригінали планів залишено без виправлень як матеріали експерименту.

За попереднім описом експерименту, у варіанті A `docs/` перейменовано на `docs_hidden/`, у варіанті B папка доступна. Самі плани містять відповідні повідомлення агента; окремий журнал файлових операцій не додано. Обидва прогони виконувалися в одному чаті, де агент уже бачив код. Точні початкові промпти та повний журнал відповідей не прикріплено до цих матеріалів, тому однаковість промптів незалежно не перевірена.

Це порівняння планів, а не виконаних реалізацій: поле тривалості в поточному API відсутнє. Реалізоване розширення для лабораторної — оцінка терміновості, яка охоплює backend, AI та Android.

## Таблиця

| Критерій | Без docs/ | З docs/ |
|---|---|---|
| Заявлені джерела | Код, повідомлення про відсутність `docs/` | Код і 4 названі документи бази знань |
| Обсяг | Backend-модель, AI, маршрут, Android DTO, ViewModel, UI | Ті самі 6 основних файлів |
| Запропоноване JSON-поле | `symptom_days` на обох сторонах | `duration_days` на backend; `durationDays` з `@SerializedName("duration_days")` або налаштуванням Gson на Android |
| Повторний запит | Явно запропоновано `lastSymptomDays` | Передавання тривалості при retry не описано |
| Необов'язковість поля | `default=None` | `default=None` |
| Старі записи історії | Описано ризик, окремого тесту читання старого JSON немає | Описано ризик, окремого тесту читання старого JSON немає |
| Валідація | Помилкова назва `422 Bad Request` у тесті; у ризиках назва правильна | Правильна назва `422 Unprocessable Entity` |
| Тип параметра Python | `description: str` | Помилково `description: String`; у Python потрібно `str` |
| Правило тривалості для AI | Пропонується поріг 7 днів | Пропонується діапазон 7–14 днів |
| Перевірки | Запропоновано ручні сценарії | Запропоновано ручні сценарії та ширший перелік припущень |

## Уточнення після звірки

- Поточна `SymptomRequest` у `backend/models.py` містить лише `description`. Обидві назви нового поля є пропозиціями; жодна ще не є чинним контрактом.
- Попереднє твердження цього порівняння про відсутність `@SerializedName` у плані з docs було помилковим: анотація прямо згадана. Якщо обрати альтернативу через Gson, її потрібно конкретизувати перед реалізацією.
- Відсутність опису retry у плані з docs — прогалина плану, а не доведена помилка виконаного коду нової функції. Функція тривалості не реалізована.
- Сумісність старих JSON-записів в обох планах заявлена, але потребує тесту; дефолтне значення в Kotlin саме по собі не є доказом усієї міграції.
- Пороги 7 та 7–14 днів — неперевірені припущення планів, які не слід подавати як підтверджені медичні правила чи очікувати гарантованого підвищення терміновості.
- Номери рядків в оригіналах історичні й можуть зміщуватися. Поточні документи звірено з кодом 12.10.2026, зокрема виправлено температуру AI з `0.2` на `0.1`. Версію документації під час кожного прогону не закріплено окремим комітом.

## Висновок

Плани мають схожий обсяг і підхід до сумісності. Варіант з docs явно посилається на базу знань і докладніше описує припущення; варіант без docs краще враховує retry. Обидва потребують перевірки перед реалізацією. Спільний чат, попередній контекст і відсутність зафіксованих версій не дозволяють із цього експерименту довести причинний вплив документації. Для відтворюваного повтору потрібні окремі чисті чати, однаковий збережений промпт і той самий commit проєкту.
