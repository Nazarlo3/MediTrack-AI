# MediTrack AI — правила роботи агента

Відповідай українською. Спочатку перевір фактичний код і git status; зберігай сторонні зміни. Для документації додатково діє docs/AGENTS.md. Робочий процес — docs/ai-instructions.md, карта системи — docs/architecture.md. Історичні записи не замінюють поточний код.

## Загальний порядок роботи

- Пріоритети: правильність і надійність, швидкість без втрати якості, мінімальні зміни, підтримуваність і відповідні перевірки. Доводь погоджену задачу до результату, а не лише до плану.
- Читай лише потрібні файли; не перечитуй незмінене й не скануй весь репозиторій для локальної задачі. Не вигадуй функцій, API, залежностей або результатів.
- Тривіальні зміни виконуй одразу; для середніх достатньо короткого плану. Значні архітектурні рішення спочатку оцінюй за залежностями, ризиками та наслідками.
- Шукай відповіді в репозиторії перед запитанням. Самостійно обирай безпечні зворотні кроки; не перепитуй дозволу на вже погоджені дії. Не створюй зайвих абстракцій і дубльованої функціональності.

## Межі

- app/ — Kotlin/Compose, backend/ — FastAPI/Groq. Android-правила не нав'язують структуру Python.
- Для значущої задачі запиши короткий план/файли й ченджлог у docs/impl/. Виконуй погоджену задачу без повторних підтверджень звичайних кроків.
- Commit, push, deploy, реліз і платні ресурси потребують прямого дозволу. Ця інструкція його не надає.
- Видалення важливих даних, незворотні/руйнівні дії, значні архітектурні зміни з істотними наслідками та значні нові залежності також потребують підтвердження, якщо вони ще не погоджені. Не виходь за межі задачі; не обходь обмеження середовища чи відмову в доступі.
- Не скидай, не очищай і не перезаписуй сторонні зміни. Віддавай перевагу точковим правкам; додавати залежності можна лише з обґрунтуванням, без дублювання наявних можливостей.
- Не додавай ключі, медичні тексти, приватні налаштування чи docs/various files у Git/логи/діагностику. Не очищай дані телефона для перевірки.

## Android: напрям для нових і змінених ділянок

- Збережи manual DI у MediTrackApplication/SymptomDependencies. Підставляй залежності через конструктор; нові джерела даних приховуй за репозиторієм. Не створюй їх у composable чи ViewModel.
- Екран отримує стан і передає дії; ViewModel координує сценарій, data-шар працює з Android API/мережею/диском. Для нових ViewModel віддавай перевагу ViewModel замість AndroidViewModel.
- Збирай Flow з урахуванням lifecycle; відрізняй короткий UI-стан, відновлення після повороту та після завершення процесу. Не відновлюй автоматично медичні тексти без визначеної політики зберігання.
- Використовуй наявні MaterialTheme/типографіку, спільні компоненти та ресурси рядків для нового UI. Перевіряй loading/error/empty/success і доступність зміненого сценарію.
- Не проводь повний рефакторинг у межах локального виправлення. Room, DataStore, Hilt, Navigation та нові модулі — рішення під конкретну задачу, а не обов'язкові ознаки якості.
- Зберігай наявний Kotlin/Compose/Material стиль, навігацію та функції. Не блокуй головний потік, не додавай повторних запитів/зайвих перерахунків; remember використовуй лише для відповідного UI-стану. Gradle/SDK/плагіни змінюй тільки з конкретною причиною; мережеву безпеку не послаблюй.
- Зміни сховища потребують сумісності/міграції; зміни API — перевірки обох сторін і docs/api-contract.md. Збережи сценарії ліків/нагадувань, поточний вибір збору даних та попередні записи.

## Backend та AI

- Дотримуйся структури FastAPI й чинного контракту. Перевіряй вхідні дані, обробляй очікувані помилки, тайм-аути, квоти провайдера та некоректні відповіді; не логуй їхній чутливий вміст.
- Секрети — лише приватна серверна конфігурація/середовище, не код, промпти чи Git. Підтримуй сумісність Android ↔ backend; після зміни API онови контракт і відповідні регресії.
- Не вважай AI безпомилковим і не покладайся лише на мовну модель у визначенні невідкладних станів. За неможливого/невизначеного аналізу забезпечуй безпечну явну поведінку.

## Skills і перевірки

Для Android-архітектури та рефакторингу прочитай .agents/skills/meditrack-android/SKILL.md. Для цільового performance-аудиту — jetpack-compose-performance; для дозволів/експортованих компонентів — android-permissions-security. Читай лише застосовні references. Локальна адаптація та джерело Google — docs/android-guidelines.md; не припускай підтримку нових API лише тому, що вони згадані у skill.

- Документація/skills: перевір посилання, валідність skill, узгодженість і diff; збірка не потрібна.
- Зміна логіки: відповідна регресія та тести зміненого шару. UI/lifecycle/сховище — також компіляція/збірка, коли потрібна. Повторюй лише через нову зміну або невирішену помилку.
- Для великих змін архітектури, міграцій, API чи нагадувань перевір пов'язані компоненти, збери змінені модулі та виконай доступний lint/статичний аналіз. Не запускай весь набір для кожної дрібної зміни.
- При збої прочитай помилку, визнач причину й зв'язок зі змінами, виправ власну помилку та повтори потрібну перевірку. Не повторюй невдалу команду без причини; чесно повідомляй залишкові проблеми.
- Android: .\gradlew.bat :app:testDebugUnitTest; :app:assembleDebug; :app:lintDebug — обирай потрібні задачі, не всі автоматично. JDK — Android Studio jbr; SDK — local.properties, не жорстко заданий шлях іншого ПК.
- Backend: python -B -X utf8 -m unittest discover -s backend/tests. Live Groq/Google та телефонні зміни не входять до звичайного unit-прогону.
- Наприкінці: що змінено, фактично виконані перевірки та межі. Не називай функцію перевіреною за самою наявністю коду або старим журналом.
- Завершення означає реалізований запит, враховані ризики регресій, виконані доречні перевірки або пояснені перешкоди й відсутність сторонніх правок. Підсумок — коротко українською, з важливими файлами та невирішеними питаннями.
